Forge needs two distinct execution boundaries, because they answer different questions.

## Agent and generated-code isolation

[Fly's agent architecture](https://fly.io/ai-agents/) separates an agent process from the code it runs and places isolated execution in Firecracker microVMs. [Fly's platform architecture](https://fly.io/docs/reference/architecture/) describes the same hardware-virtualized substrate for application workloads. This is a useful target for Forge's planner, builder, local tool, and evaluator worker seam: generated code can receive a bounded filesystem, network policy, resource budget, and disposable checkpoint without receiving Studio credentials or mutation authority.

Fly's public homepage associates Lemonade with Fly. That supports only the claim that Lemonade is a Fly customer; it does not reveal whether Lemonade's Roblox product uses one VM per task, how it drives Studio, or where it grades gameplay. Forge must not infer a private competitor topology from a customer logo.

## Roblox engine authority

Roblox's [`StudioTestService`](https://create.roblox.com/docs/reference/engine/classes/StudioTestService) exposes `ExecutePlayModeAsync`, `EndTest`, and test arguments for programmatic tests. Roblox's [Studio testing modes](https://create.roblox.com/docs/studio/testing-modes) separately define ordinary creator-driven Test/Stop and explicitly describe solo Play as separate client and server simulations. [`RunService`](https://create.roblox.com/docs/reference/engine/classes/RunService) distinguishes Edit, Play Server, and Play Client contexts. A Roblox staff explanation of the [plugin lifecycle across data models](https://devforum.roblox.com/t/plugin-changes-are-only-interpreted-when-i-exit-and-re-enter-studio/1993588/4) confirms that plugins load in Edit, run in Play Client/Server data models, and unload those Play instances on Stop. The consumed hinge run demonstrated the architectural consequence: an in-memory Edit connector cannot observe a complete ordinary Play→Stop transaction by adding more property signals or polling. A Linux microVM likewise cannot independently reproduce the user's current Studio place, plugin security context, Change History transaction, client/server simulation, or engine implementation.

Forge therefore treats real Studio as a separate proof worker. The control plane sends one canonical, hash-bound data plan. Registered experiments may use the programmatic `StudioTestService` lifecycle. Creator verification persists and reads back one exact passive arm while leaving the editable place untouched. The Play Server connector independently resumes that arm in its disposable data model, installs bounded diagnostics and a direct manifest-dispatched observer, performs synchronous target/one-shot reads, samples every series through one Heartbeat connection, and writes a terminal receipt before transport. It creates no Script and parses no printed result; LogService is diagnostics-only. After Stop, the Edit connector changes only that exact receipt into an inert replay-only acknowledgement tombstone when the backend explicitly finalizes it; physical cleanup waits for durable mutation-finalization acknowledgement. A Stop-sealed incomplete run remains blocked until the creator explicitly authorizes a hash-bound same-transaction retry or cancellation. No in-memory object is treated as if it crossed data models. A future microVM may compile, statically check, or grade the returned envelope, but it cannot manufacture it or replace Studio authority.

## Consequence for creator interaction checks

The runtime proof program must be executable before Studio mutation begins. Resolution calls precede dependent observations; series schedule capacity and a maximum creator-observation window fit one explicit budget; and the exact post-mutation revision-bound artifact is persisted before Forge silently arms the first Play. The common generated Studio policy permits at most five minutes and creator interaction checks reserve at most 90 seconds within it. Waiting for the human start is outside that machine deadline. Returning to Edit mode seals the actual in-memory sample prefix, so sample counts shown for creator series are explicit upper bounds. An authoritative absent target is complete evidence and can fail the behavior check; unavailable/read-error facts are incomplete. Incomplete technical evidence preserves the provisional mutation and exposes explicit Retry/Cancel; it cannot silently loop, become a mismatch, or cause automatic rollback.
